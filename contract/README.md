# contract — формат разметки карты

Единственное, о чём договариваются разметчик, клиент и сервер: **что именно лежит
в `annotation.json`**.

Описание формата человеческим языком — [FORMAT.md](FORMAT.md), правила соседства проектов —
[docs/projects.md](../docs/projects.md).

## Что здесь лежит

| Файл | Что это |
|---|---|
| `annotation.v1.schema.json` | машинная схема версии 1: поля, типы, обязательность, закрытые списки, пределы |
| `annotation.v1.example.json` | пример из [FORMAT.md](FORMAT.md) §16 один в один; на нём сходятся оба валидатора |
| `cases/` | набор плохих случаев: папка на нарушение, рядом ожидаемый вердикт |
| `CHANGELOG.md` | журнал изменений: что добавилось, что сломалось, когда |
| `FORMAT.md` | что именно выдаёт разметка: состав, координаты, сетка, проверка |
| `README.md` | этот файл: правила изменения контракта и коды отказов |

## Правила

1. **Владелец формата — сервер.** Разметчик подстраивается под формат, а не наоборот.
2. **Формат версионируется.** Старые разметки читаются после обновления сервера;
   несовместимое изменение — новая версия файла, а не правка старого.
3. **Результат разметки — недоверенный вход, кто бы его ни сделал.** Сервер проверяет файл
   сам: размеры, границы, отсутствие лишнего. Производителем может быть утилита на машине
   мастера, рука мастера с мышкой или будущий чужой инструмент — для сервера это один и тот же
   файл, и поля «кто произвёл» в формате нет. Поэтому валидаторов два (Python в разметчике, Go
   в сервере), и они обязаны одинаково читать один и тот же пример и один и тот же набор плохих
   случаев.
4. **Тишина — не согласие.** Поля, которого нет в схеме, — ошибка, а не «ну ладно».

**Чего в контракте нет.** Предварительного файла `annotation.preview.json`: он содержит тот же
результат плюс числа уверенности и нужен только разметчику и клиенту. Схемы у него нет, сервер
его не принимает, и меняться он может свободно, пока эти двое договариваются между собой.

## Коды отказов

Закрытый список: вердикт либо `ok`, либо `error` с одним из кодов. Код — для машины и для
сравнения двух валидаторов, текст рядом — для человека.

| Код | Что случилось |
|---|---|
| `not_json` | файл не разбирается как JSON |
| `non_finite_number` | в файле `NaN` или `Infinity` |
| `schema` | форма не соответствует схеме: поле, тип, обязательность, список значений |
| `too_many_elements` | стен, дверей или областей больше предела |
| `image_too_large` | картинка больше 8192 по стороне |
| `image_size_mismatch` | размер в файле не совпал с присланной картинкой |
| `image_sha256_mismatch` | `sha256` в файле не совпал с присланной картинкой |
| `duplicate_id` | `id` повторяется внутри коллекции |
| `zero_length_segment` | у стены или у двери совпали концы |
| `polygon_not_closed` | последняя пара полигона не повторяет первую |
| `point_outside_image` | координата за пределами картинки |
| `door_wall_missing` | `wall_id` указывает на стену, которой нет в файле |
| `door_not_on_wall` | дверь не лежит на своей стене (концы и середина, допуск 2 px) |

Ошибка формы приходит с кодом `schema`, кроме двух случаев, где у предела свой код: так
«слишком много стен» не путается с «поле не того типа».

## Как проверять

```sh
pip install 'jsonschema==4.*'
python3 scripts/validate_annotation.py contract/annotation.v1.example.json
python3 scripts/validate_annotation.py --cases contract/cases
python3 scripts/check_limits.py
```

Вердикт — одна строка JSON: `{"verdict": "ok", "code": null, "message": "…"}`. Код возврата:
0 — годен, 1 — отказ, 2 — беда с запуском (нет файла, нет схемы).

**Случай** — папка в `cases/`:

| Файл | Что это |
|---|---|
| `annotation.json` | файл с одним нарушением (или годный, как `ok-example`) |
| `expect.json` | ожидание: `{"verdict": "error", "code": "door_not_on_wall"}` и поле `what` для человека |
| `image.json` | необязателен: что сервер получил картинкой — `width`, `height`, `sha256` |

`image.json` заменяет саму картинку: проверке нужны её размер и хеш, а не пиксели, и держать
десяток одинаковых PNG в git незачем. В самом примере `sha256` нет намеренно: картинки рядом
с ним тоже нет, а придуманный хеш хуже отсутствующего — отсутствие поля разрешено, а неверное
значение нет. Пары случаев «на границе» — `point-last-pixel` рядом с `point-outside-image`,
`image-sha256-match` рядом с `image-sha256-mismatch` — проверяют, что правило срабатывает
на единицу, а не «примерно там».

Пределы проверяются отдельно, `scripts/check_limits.py`: файл на 20 001 стену строится
в памяти, потому что держать мегабайт в git ради одного отказа не нужно.

## Состояние

Схема, пример, проверка и набор случаев есть; CI гоняет их на каждой правке в `contract/`.
Сходиться пока нечему: второй валидатор — Go в сервере — появится вместе с сервером, и до тех
пор правило «оба валидатора читают один набор» держится на одной стороне
([../docs/open-questions.md](../docs/open-questions.md), «Формат карты»).
