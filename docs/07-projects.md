# 07. Из чего состоит проект

> **Зачем.** Разработка идёт кусками: пока не сделан разметчик, серверу нечего проверять,
> а клиенту нечего рисовать. Значит нужны границы, по которым можно работать над одной частью,
> не трогая остальные, и одна точка, через которую части договариваются.
>
> **Статус: решено** (D33, D34). Кода в репозитории пока нет — есть только каркасы проектов.

## 1. Части и папки

| Папка | Что это | На чём | Где работает | Состояние |
|---|---|---|---|---|
| `docs/` | требования, решения, открытые вопросы | markdown | нигде | 7 документов, D01–D36 |
| `contract/` | формат разметки карты: схема, пример, журнал версий | json | нигде, это данные | каркас |
| `annotator/` | разметчик карт: картинка → `annotation.json` | Python, numpy, Pillow (Q43) | машина мастера, запускает клиент (D35) | каркас |
| `server/` | игра (443) и панель администратора (8443) | Go | VPS: 1 ядро, 512 МБ, без видеокарты | каркас |
| `client/` | стол и карта: программа клиента, а не страница (D36) | не выбран | машина мастера и машины игроков | каркас |

Слово «разметчик» в коде — `annotator`. Не `recognizer` (это про речь) и не `parser`
(это про текст): разметчик **размечает карту**, то есть превращает картинку в описание.

**Не проекты.** Документы — не проект, у них нет сборки. Панель администратора и игра —
не два проекта: это один бинарь с двумя режимами запуска (D22), разделённый на два процесса
только чтобы падение одного не уносило другой. Панель при этом остаётся страницей в браузере:
она не запускает процессов на машине пользователя, поэтому D36 её не касается.

## 2. Чем части связаны

Связей ровно три, и все они — контракты, а не общий код:

1. **Файл разметки** `annotation.json` версии 1 — вход сервера и клиента, выход разметчика.
   Владелец формата — сервер (D11), описание — [05](05-map-annotation.md), машинная схема —
   `contract/`. Результат разметчика для сервера — недоверенный вход: сервер проверяет его
   сам, независимо от того, кто произвёл.
2. **Командная строка разметчика** — `vtt-annotate --image <карта> --out <annotation.json>`.
   Это граница между клиентом и разметчиком, а не между сервером и разметчиком: клиент
   запускает процесс на машине мастера и ждёт его (D35), поэтому граница — процесс,
   а не вызов функции. Прогресс — в stderr, результат — в файле, сеть и порт разметчику
   не нужны вовсе.
3. **Сетевой API сервера** — HTTP для входа и загрузки, WebSocket для стола. Его потребитель —
   клиент, включая будущий чужой. Поэтому ответы сервера описываются так, чтобы
   по описанию можно было написать вторую реализацию (D06), а не «как получилось».

```
карта.jpg ──> annotator ──> annotation.json ──> server ──> client (игрок)
                   ▲                         проверка
                   └── client (мастер): запускает процесс и ждёт результат

contract: формат файла (annotation.json) и API сервера — то, о чём договариваются все
```

## 3. Правила независимости

Их шесть, и они проверяемые, а не «постараемся»:

1. **Никаких перекрёстных импортов.** `server/` не импортирует ничего из `annotator/`
   и наоборот. Единственное, что у них общее, — файлы в `contract/`.
2. **У каждого проекта свой манифест и своя команда сборки:** `annotator/pyproject.toml`,
   `server/go.mod`, у `client/` — манифест того стека, который выберут (он ещё не выбран,
   §6). В корне репозитория манифестов нет.
3. **Каждый проект собирается и проверяется на чистой машине по своему README.** Если для
   проверки `annotator/` нужен Go, а для `server/` — Python, граница проведена неправильно.
4. **CI по путям:** правка в `annotator/**` запускает только его тесты; правка в `contract/**`
   запускает контрактные тесты всех потребителей (сейчас это `annotator/` и `server/`),
   потому что она касается всех.
5. **Контракт меняется только с версией.** Новое поле — новый пункт в `contract/CHANGELOG.md`;
   несовместимое изменение — новая версия формата, старая продолжает читаться (D11).
6. **Планирование не смешивается.** Задачи помечаются префиксом проекта (`annotator:`,
   `server:`), чтобы «сделать стены» не висело в одном списке с «настроить TLS».

## 4. Когда всё-таки режем на репозитории

Монорепо выбран не навсегда, а пока нет причины его разрезать (D33). Причины, каждая
из которых самодостаточна:

- **чужая лицензия или публикация наружу** — например, разметчик отдают как отдельную
  открытую утилиту;
- **тяжёлые файлы моделей** — распознавание речи или нейросетевая разметка: десятки-сотни
  мегабайт не должны утяжелять клон;
- **разные права доступа** — внешний контрибьютор на клиенте при закрытом сервере;
- **разные релизные циклы при уже стабильном контракте**.

Разный язык — не причина: Go, Python и TypeScript спокойно живут в одном репозитории,
если у каждого своя сборка. Если причина появилась, контракт выносится как **версионируемый
артефакт** (тег вида `contract/v1`, копия в проекте с проверкой версии), а не сабмодулем:
сабмодуль требует синхронного коммита в двух местах и ломает сборку у того, кто забыл.

## 5. Что было и куда делось

До этого решения в репозитории лежал прототип: `tools/` (три скрипта), `schema/` (схема
и пример) и `tests/` (6 карт с фикстурами, 21 МБ). Он снят с рабочего дерева (D34), потому
что писался под эксперимент и будет переписан внутри `annotator/` и `contract/`.

Восстановить любой файл: `git show 2c504fb:tools/validate_annotation.py`. Знание, которое
в нём было, перенесено в документы: размеры, шаги сетки и ловушки карт — [04](04-experiment-map-layout.md),
§5; числа проверки напечатанной сетки — [05](05-map-annotation.md), §5.2; правило
«эталон синтетический» — D32.

## 6. Что здесь не решено

- **Стек клиента** не выбран (D36 говорит «программа», но не «какая программа»). Это отдельное
  решение со своими доводами, и принимать его «попутно со структурой» значит выбрать его
  без доводов. Ограничение, которое уже есть: клиент запускает процессы и читает их вывод
  (D35), поэтому страницей в браузере он быть не может.
- **Как клиент попадает к людям и как обновляется** — [Q42](03-open-questions.md). Раньше
  ставить ничего не было нужно, теперь клиент — первая вещь, которую ставит каждый игрок.
- **На чём написан разметчик и как его раздавать** — [Q43](03-open-questions.md): Python
  удобнее для эксперимента, Go легче по весу (≈ 10 МБ против ≈ 70 МБ).
- **Нужен ли отдельный проект под распознавание речи.** Сейчас по D13 это модель внутри
  клиента, а не сервис. Отдельный репозиторий понадобится только когда появится конкретная
  модель с чужими файлами и лицензией.
- **Кто проверяет формат на стороне сервера и как согласованы валидаторы** (Python
  в разметчике, Go в сервере, позже — в клиенте), чтобы они не разошлись в трактовке схемы.
