# launcher — установка и обновление клиента

Одна программа, которую человек запускает сам: она ставит клиент и его пакеты, приводит их
к нужной версии и только потом запускает клиент. Инсталлер — её первая роль; после установки
она остаётся рядом и работает лаунчером.

**Где живёт.** На машине каждого участника стола, рядом с клиентом, в одном каталоге установки.
Это единственная программа проекта, которая стоит у всех: клиент ставят все, сервер — один
человек, разметчик — только мастер и только по желанию.

## Границы

- **Не часть клиента.** Отдельная программа и отдельный проект. Она работает, когда клиента ещё
  нет или он сломан, и переживает замену клиента — в этом весь смысл. Клиент не может заменить
  сам себя: на Windows работающий `.exe` не перезаписать, а «обновиться во временную копию
  и перезапуститься» — отдельный механизм с правами и откатом.
- **Ни одного адреса сервера.** Вход лаунчера — манифест и файлы рядом с ним
  ([MANIFEST.md](MANIFEST.md)). К серверу игры он не обращается: ни за версиями, ни за
  разрешением на запуск, ни за списком пакетов. Лаунчер запускается первым — до того как человек
  выбрал сервер и вошёл, — и физически не может спросить сервер «какая версия нужна». «Нужна
  версия не ниже X» — ответ сервера клиенту при подключении, а не входные данные обновления:
  манифест говорит, что есть, сервер — что требуется; разошлись — человек видит отказ на входе
  с номером версии, а не посреди боя.
- **Не решает, чего человеку не хватает.** Ставит то, что записано в манифесте: `client`
  обязательно, `voice` и `annotator` — только действием человека. Молча доставляется только
  обязательное.
- **Не сервер.** `vtt install`, `vtt update`, `vtt migrate` — подкоманды серверного бинаря.
  Общее слово «обновление» не делает их одной программой: у сервера обновляются база и миграции,
  у клиента — файлы.
- **Секретов не хранит.** Ни ключей, ни паролей, ни адресов: только файлы поставки и их хеши.
- **Подписи сверх `sha256` нет.** Доверие к файлу — доверие к аккаунту: проверяются размер
  и `sha256` из манифеста. Хеш ловит порчу файла и обрыв скачивания — то, ради чего он и стоит;
  подпись защищает от подмены на стороне хостинга, но этот сценарий начинается там, где у нас уже
  нет ни аккаунта, ни раздачи, а ключ, его хранение и ротация — работа без пользы, пока пакеты
  приходят из одного релиза.
- **Написан на Go, только стандартная библиотека.** Один бинарь без рантайма, целевая сборка —
  `windows/amd64` под именем `vtt-launcher-<v>-win64.exe`, тесты идут на Linux. Он запускается
  первым на машине, где может не быть вообще ничего, поэтому рантайм, который он должен сам себе
  поставить, — не вариант. Go даёт бинарь без зависимостей и тот же язык, что у сервера. Отказ
  от зависимостей — не аскетизм: лаунчер обновляется вручную, и чем меньше в нём чужого кода,
  тем реже повод его менять. `go.sum` нет и не появится без отдельного решения: внешняя
  зависимость здесь — не строка в файле, а размер и чужой код в единственной программе, которая
  работает до установки.

## Что внутри

| Пакет | Задача |
|---|---|
| `internal/manifest` | прочитать `latest.json`, проверить версию формата, собрать список файлов |
| `internal/fetch` | скачать недостающее, сверить размер и `sha256`, докачать после обрыва |
| `internal/unpack` | разложить архив в каталог версии, не пуская записи за его пределы |
| `internal/store` | каталог установки: `state.json`, версии рядом, включение переключением |
| `internal/launch` | запустить клиент, дождаться выхода, вернуть его код |
| `internal/app` | порядок действий: манифест → файлы → раскладка → клиент; режимы `--check`, `--install` |
| `cmd/vtt-launcher` | командная строка: флаги, коды возврата, версия |

Правило раскладки одно: старые файлы не перезаписываются на месте. Новая версия скачивается
рядом, проверяется и включается одним переключением; не получилось — остаётся прежняя. Иначе
обрыв на середине оставит человека без клиента вместо прошлой версии.

```
<каталог установки>/
  state.json                  что включено сейчас
  versions/client-1.4.0/…     включённая версия: client.exe и файлы рядом
  versions/client-1.3.0/…     предыдущая, рядом на случай отката
  tmp/                        скачивание и распаковка; успешный запуск его чистит
```

## Интерфейс (то, о чём договариваемся с клиентом)

```sh
vtt-launcher                            # доставить недостающее и запустить клиент
vtt-launcher --check                    # сказать версии и чего не хватает, ничего не менять
vtt-launcher --install <каталог|архив>  # поставить из файла, без сети
vtt-launcher --packages voice,annotator # доставить необязательные пакеты по просьбе человека
```

- лаунчер передаёт клиенту каталог установки (`--install-dir=<каталог>`), клиент отвечает
  на `--version`; больше между ними ничего нет — ни сокета, ни порта. Та же граница, что
  у разметчика, и по той же причине: это две программы, а не одна;
- точка входа пакета — файл с именем пакета внутри его версии: `client.exe` (на Linux — `client`).
  Имя — часть раскладки, а не догадка: лаунчер не ищет «какой-нибудь exe» в архиве;
- сеть не нужна ни для `--check`, ни для `--install`: игровой вечер без интернета не должен
  зависеть от доступности чужого сайта;
- вывод — человеческий текст на экран и в журнал рядом с установкой; код возврата: 0 — сделали,
  что просили, 1 — доставить не удалось (сети нет, хеш не сошёлся, нет места), 2 — доставили,
  но запустить не удалось. Код самого клиента лаунчер не подменяет своим: он его печатает
  и выходит с 0 — «сделали, что просили», а не «игра прошла удачно».

## Состояние

Код есть: командная строка, строгий разбор манифеста, скачивание с докачкой, проверка `sha256`
и размера, раскладка версий рядом и запуск клиента — с тестами на каждый шаг. Чего нет:
инсталлера (понадобится к первой раздаче людям) и настоящего клиента, поэтому запуск проверяется
на подставной программе. Формат `latest.json` — [MANIFEST.md](MANIFEST.md). Место в репозитории
и правила соседства — [../docs/projects.md](../docs/projects.md).

## Сборка и проверка

```sh
cd launcher
go build ./...   # всё собирается
go vet ./...     # подозрительные места
go test ./...    # пакеты и сквозные сценарии
gofmt -l .       # пусто — значит отформатировано

# то, что попадёт в релиз: windows/amd64, без cgo, версия из тега
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -trimpath \
  -ldflags "-s -w -X main.version=v0.1.0" -o bin/vtt-launcher.exe ./cmd/vtt-launcher
```

Тесты не ходят в настоящий GitHub и не требуют сети: манифест и файлы отдаёт транспорт в памяти,
а клиент в тестах — сам тестовый бинарь, который отвечает на `--version` и оставляет след запуска.
Поэтому нет ни поддельного сервера, ни ожидания таймаутов.

## Обновление самого лаунчера

Обновляется всё, кроме той программы, которая обновляет: в первой версии новую версию лаунчера
человек ставит сам, новым инсталлером, и сам себе лаунчер ничего не скачивает. Автоматическое
самообновление — это права, откат и «а если новая версия не запустится», то есть ровно та работа,
от которой ушли, вынеся обновление из клиента. Работа лаунчера — прочитать манифест, сверить
`sha256` и запустить; меняется он редко, поэтому ручное обновление стоит почти ничего.

Поэтому записи `launcher` в `latest.json` нет — манифест описывает поставку клиента, а не
установщик. Пакетов, кроме `client`, `voice` и `annotator`, манифест не знает, и незнакомое имя
остаётся ошибкой разбора. Пакета подготовки карты в списке пока нет: один это пакет с разметчиком
или два — ещё не решено. Появится нужда обновлять лаунчер автоматически — это новое правило
и новая версия формата, а не тихое поле в манифесте.
