# server — игра и панель администратора

Один бинарь, два режима запуска:

| Режим | Порт | Что делает | Судьба при падении |
|---|---|---|---|
| `vtt --mode=game` | 443 | кампании, столы, WebSocket, туман, фишки | падает только игра |
| `vtt --mode=admin` | 8443 | вход администратора, нагрузка, обновление, логи | падение игры не отбирает панель |

Падение игры или OOM-killer за игрой не должны отбирать панель, которой эту игру чинят. Два
разных бинаря дали бы риск рассинхрона версий, а один процесс — общую судьбу, поэтому артефакт
один, а юнитов два: у каждого свои лимиты памяти и свой `Restart`. База общая, в режиме WAL;
состояние игры панель читает из файла-пульса, а не из базы.

## Границы

- **Целевая машина: 1 ядро, 512 МБ, без видеокарты, Debian.** Подготовка и разметка карт в этот
  бюджет не входят: их считает машина мастера. Если на сервере появится своя тяжёлая работа, она
  живёт отдельным процессом с урезанным CPU, а игровому серверу отдан приоритет: домашний сервер —
  одна машина на всё, и фоновая задача не должна забирать ядро посреди боя. Сейчас в этом списке
  ничего нет: бэкап и миграции — короткие операции по расписанию.
- **Разметку сервер не придумывает.** Он получает пару «картинка и `annotation.json`», проверяет
  файл по схеме из `../contract/`, считает хеш картинки сам и создаёт сцену. Кто произвёл файл —
  разметчик на машине мастера, рука мастера или будущий чужой инструмент — сервер не знает и не
  должен знать. Отдельной «доверенной» ветки проверки для своего результата нет.
- **Картинки живут в библиотеке кампании, а не при сцене.** Один файл — одна копия, сколько бы
  сцен на него ни смотрело; повторный импорт того же файла узнаётся по хешу, который сервер
  посчитал сам. Удаление сцены картинку не удаляет: её могут использовать другие сцены. Чистка
  неиспользуемых — не первая версия.
- **Решает сервер, а не клиент.** Всё, что попадает в клиент или в браузер, доступно человеку,
  поэтому секреты, в том числе стены до открытия, не приходят ни в клиент, ни в браузер.
- **Никаких чужих облаков** для картинок и звука.
- **Администратор видит нагрузку, но не содержимое.** Ему доступны загрузка процессора, памяти
  и диска, время работы задач, длина очереди фоновых задач и число подключённых. Названий
  кампаний и того, что именно делают люди, — нет: в админском экране цифры и обезличенные задачи.

## Панель и эксплуатация

- **Открыта в интернет по умолчанию:** `https://<IP>:8443`, логин + пароль + второй фактор,
  настоящий сертификат на IP, порт 80 открыт постоянно. Панель нужна ровно тогда, когда всё
  сломалось, а туннель — лишняя точка отказа и требует клиента на каждом устройстве. Режимы
  `wg` и `local` остаются для тех, кому так спокойнее; там сертификат самоподписанный.
- **Вход ограничен по памяти и по попыткам.** Пароль — Argon2id; одновременных проверок
  не больше одной, остальные ждут или получают «занято». Одна проверка — это десятки мегабайт,
  и без потолка двадцать попыток складываются в OOM, а ядро убивает не панель, а игровой стол.
- **Второй фактор включён по умолчанию, но не навязан:** шесть цифр из приложения, backup-коды,
  сброс по SSH с записью в журнал. Первый вход ночью не должен превращаться в квест «где взять
  приложение», но человек, который ничего не настраивал, всё равно оказывается с двумя факторами.
- **Обновление — одна команда, и неудачная миграция не оставляет полубазы.** Один бинарь,
  миграции внутри него (`go:embed`), каждая миграция в транзакции. Порядок: проверка контрольной
  суммы → бэкап базы → `--mode=migrate` → замена бинаря (старый остаётся как `vtt.prev`) →
  перезапуск обоих юнитов → health-check 30 секунд → автоматический возврат `vtt.prev`, если
  не поднялось. Миграции только вперёд; назад — из бэкапа осознанной командой. Если схема новее,
  чем понимает бинарь, он не стартует с понятным текстом. Панель никогда не мигрирует и никогда
  не обновляется кнопкой из интернета.
- **Обновление запускается командой по SSH.** Кнопка «обновиться» в панели, доступной
  из интернета, — это «дай мне подменить бинарь», и до появления подписи релизов её нет.

Подробности — [ADMIN.md](ADMIN.md): вход, сертификат, сессии, журнал, аварии.

## Сборка и проверка

```sh
cd server
gofmt -l .                                   # пусто — значит отформатировано
go vet ./...
CGO_ENABLED=0 go test ./...                  # контракт, пределы, API и база
CGO_ENABLED=0 go build -trimpath -o vtt ./cmd/vtt   # статический бинарь
file vtt                                     # ELF … statically linked
./vtt --version
./vtt --mode=game --schema=../contract/annotation.v1.schema.json

./vtt --db=vtt.db --create-account=alice     # пароль из stdin
./vtt --db=vtt.db --mode=game --listen=127.0.0.1:8080
```

Тесты читают `../contract/annotation.v1.schema.json` и `../contract/cases/`: схема и случаи
у Go и Python — одни и те же файлы, и второй копии нет, потому что копии расходятся молча.
Сходятся они и по ответу: `python3 scripts/validate_annotation.py --cases contract/cases`
и `go test ./...` обязаны назвать на каждом случае один вердикт и один код.

Схема читается с диска, а не вшита в бинарь через `go:embed`: вшитая копия жила бы внутри
`server/` и разошлась бы с `contract/` тихо. Внутрь она переедет вместе с импортом карт — тогда
и станет видно, как бинарь получает `contract/` на целевой машине.

## База и драйвер

Драйвер — `modernc.org/sqlite`: тот же SQLite, переведённый на Go. Выбор из-за поставки, а не
скорости: сервер собирается с `CGO_ENABLED=0` и остаётся статическим бинарём, которому не нужен
ни gcc, ни glibc машины сборки. С cgo-драйвером бинарь, собранный на Ubuntu 24.04, не запустился
бы на Debian 12 из-за glibc, а нагрузка здесь — несколько человек, и разница в скорости между
драйверами не наблюдаема.

Схема — миграции в `internal/storage/migrations`, вшитые в бинарь через `go:embed`; применяются
при старте, каждая в своей транзакции, только вперёд. Пароль — Argon2id (64 МиБ, одна проверка
за раз: потолок держит `internal/api`). Сессии — в той же базе, срок 30 суток.

## Что здесь будет

Go-модуль, точка входа `cmd/vtt`. Первый шаг сделан: скелет с двумя режимами, проверка контракта,
первый срез API и база SQLite за интерфейсами `Directory` и `Sessions`. Дальше — кампании
и приглашения, импорт карт и стол по WebSocket.

Сетевое API описано заранее — [API.md](API.md): вход, кампании, приглашения, библиотека картинок,
сцены, видимость и WebSocket стола. По нему пишется и сервер, и клиент, поэтому спор о поведении
решается правкой описания, а не разговором по памяти.

Требования к поведению — [docs/how-it-works.md](../docs/how-it-works.md).

## Состояние

Есть модуль, точка входа с двумя режимами, валидатор контракта, который сходится с
Python-валидатором на общем наборе случаев, и срез API: вход, «мои кампании», кампании
с составом, загрузка картинки, импорт пары «картинка + annotation.json» и чтение сцены
(пакет `internal/api`, случаи — `internal/api/testdata/cases`). База SQLite
(пакет `internal/storage`: аккаунты, кампании, членство, сессии, картинки, сцены) и режим `game`:
сервер слушает, когда дан `--listen`. Аккаунт заводится командой `--create-account` — это
временный путь до панели. WebSocket, токены, видимость, вход администратора и панели нет:
README фиксирует границы, чтобы `server/`, `annotator/` и `client/` не начали протекать друг
в друга (правила — [docs/projects.md](../docs/projects.md)).
