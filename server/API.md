# API сервера — версия 1

> **Зачем.** Клиент — вторая реализация по этому описанию, а не «как получилось»: чужой клиент
> должен подключаться к тому же серверу, не читая наш код. Поведение стола описано в
> [../docs/how-it-works.md](../docs/how-it-works.md), формат разметки — в
> [../contract/FORMAT.md](../contract/FORMAT.md), панель администратора в это описание не входит
> ([ADMIN.md](ADMIN.md)).
>
> **Статус.** Версия 1, описана целиком. Реализованы вход и сессии, кампании,
> приглашения по коду, библиотека картинок, импорт сцены, чтение сцены, WebSocket-стол
> с `hello`, чатом, фишками с владельцем и характеристиками, показом сцены всем,
> дверями, кубами, ходом боя и туманом для игроков по фишкам. Листы персонажей,
> редактор геометрии и «исследовано» ещё описаны, но не написаны. Описание остаётся
> контрактом для клиента и сервера.

## Общее

| Что | Как |
|---|---|
| Адрес | `https://<сервер>:443/v1/…`; игра и API на одном порту, панель — отдельно на 8443 |
| Формат | JSON в UTF-8, `Content-Type: application/json`; загрузка картинки — `multipart/form-data` |
| Вход | `Authorization: Bearer <токен>`; токен приходит из `POST /v1/sessions` и живёт в файле у клиента |
| Версия | в пути (`/v1/`); незнакомая версия — `404`, устаревший клиент — `426` с `min_api` |
| Время | серверное, ISO 8601 в UTC; порядок событий — сквозной `seq`, а не часы клиента |
| Скрытое | отвечает `404`, как несуществующее: ошибка не намекает, что объект есть |

**Ошибка — всегда одна форма.** Код — для машины, текст — для человека; список кодов закрытый.

```json
{ "error": { "code": "forbidden", "message": "дверь далеко" } }
```

| Код | HTTP | Что случилось |
|---|---|---|
| `unauthorized` | 401 | нет токена, он истёк или отозван |
| `forbidden` | 403 | роль не позволяет; текст говорит, что именно |
| `not_found` | 404 | объекта нет или он скрыт от этого человека |
| `bad_request` | 400 | тело не разбирается, поля не того типа |
| `validation` | 422 | файл разметки не прошёл контракт; рядом `contract_code` из `contract/README.md` |
| `conflict` | 409 | объект уже существует или состояние не допускает действие |
| `busy` | 503 | вход занят проверкой пароля (одна одновременно) |
| `client_too_old` | 426 | клиент старее `min_api`; в ответе `min_api` и текст «нужна версия не ниже» |

**Намерение, а не состояние.** Клиент присылает, что хочет сделать, сервер решает, что вышло,
и рассылает результат. У намерения есть `intent_id` (UUID клиента): повтор после обрыва
не применяется дважды, сервер помнит последние 200 намерений на соединение и отвечает прежним
результатом.

**Списки — курсором.** `GET` коллекции возвращает `{ "items": [...], "next": "<курсор|null>" }`;
`?limit=` не больше 200, по умолчанию 50.

## Вход и аккаунт

| Метод и путь | Кто | Что делает |
|---|---|---|
| `POST /v1/sessions` | любой | `{"login": "...", "password": "..."}` → `{"token", "expires_at", "account"}` |
| `DELETE /v1/sessions/current` | вошедший | отзывает текущий токен |
| `GET /v1/me` | вошедший | аккаунт и список кампаний с ролью в каждой |
| `POST /v1/accounts/lookup` | вошедший | `{"login": "..."}` → `{"id", "login"}` для адресного приглашения |

Токен — bearer, срок 30 суток, отзыв «разлогинить везде» действует на все сессии аккаунта.
Одинаковый ответ на несуществующий логин и неверный пароль; занятая проверка пароля — `busy`.
Второго фактора у игрового входа нет.

Ответы этих трёх запросов — такие; это же и примеры для клиента:

```json
POST /v1/sessions → 200
{"token": "…", "expires_at": "2026-01-31T00:00:00Z", "account": {"id": "a1", "login": "alice"}}

GET /v1/me → 200
{"account": {"id": "a1", "login": "alice"},
 "campaigns": [{"id": "c1", "name": "Тени над Валдхеймом", "role": "owner"}]}

DELETE /v1/sessions/current → 204, тела нет
```

Каждый ответ закреплён случаями в `internal/api/testdata/cases`: папка — `request.json`
и `expect.json`. Их гоняет `go test ./...`, и их же может взять чужой клиент.

## Кампании и люди

| Метод и путь | Кто | Что делает |
|---|---|---|
| `GET /v1/campaigns` | вошедший | только свои кампании; в каждой `role`: `owner`, `master`, `player`, `observer` |
| `POST /v1/campaigns` | вошедший | `{"name", "system", "settings"}`; создатель — `owner` и `master` |
| `GET /v1/campaigns/{id}` | участник | кампания, состав, моя роль, `actions` |
| `PATCH /v1/campaigns/{id}` | владелец | имя, система правил, настройки |
| `DELETE /v1/campaigns/{id}` | владелец | в корзину сервера, не мгновенно |
| `POST /v1/campaigns/{id}/invites` | владелец | `{"account_id"}` — адресно; `{"code": true}` — одноразовый код |
| `GET /v1/campaigns/{id}/invites` | владелец | кто приглашён, кто принял, срок кода |
| `DELETE /v1/campaigns/{id}/invites/{invite}` | владелец | отзыв |
| `POST /v1/invites/{code}/accept` | вошедший | вступление по коду; роль — `player`, если не сказано иное |
| `PUT /v1/campaigns/{id}/members/{account}` | владелец | `{"role": "master"}` — назначить или снять мастера |
| `DELETE /v1/campaigns/{id}/members/{account}` | владелец | выгнать |

Приглашать можно только того, кто уже есть на сервере: заведение аккаунтов — отдельное действие
владельца сервера. Мастеров может быть много и они равны; владелец один и только он меняет состав,
роли и систему правил. Сейчас владелец создаёт одноразовый код на 24 часа
(`POST …/invites` с `{"code": true}`), а вошедший человек вступает по нему
(`POST /v1/invites/{code}/accept`) ролью `player`. Повторное принятие тем же человеком
идемпотентно; чужое повторное использование кода — `409 conflict`.
## Персонажи и листы

| Метод и путь | Кто | Что делает |
|---|---|---|
| `GET /v1/campaigns/{id}/characters` | участник | свои и открытые; игрок не видит скрытых |
| `POST /v1/campaigns/{id}/characters` | мастер | лист монстра, NPC или персонажа игрока |
| `GET /v1/campaigns/{id}/characters/{cid}` | владелец листа, мастер, наблюдатель | поля листа |
| `PATCH /v1/campaigns/{id}/characters/{cid}` | владелец листа, мастер | только списком изменений полей |

Изменение адресовано полю, а не листу: `{"changes": [{"path": "hp.current", "value": 7}]}`.
Порядок изменений в теле — порядок применения; сервер рассылает каждое отдельным событием
с автором. «Последним пришло — последним легло», номеров версий у полей нет. Чужие поля игрок
не меняет, свои — свободно, включая урон по себе. Утверждение персонажа — флаг `approved`,
его ставит мастер.

## Библиотека картинок и импорт

| Метод и путь | Кто | Что делает |
|---|---|---|
| `GET /v1/campaigns/{id}/images` | мастер | библиотека задников: `id`, `sha256`, размеры |
| `POST /v1/campaigns/{id}/images` | мастер | `multipart`: `image`; второй копии по `sha256` не появляется |
| `POST /v1/campaigns/{id}/scenes:import` | мастер | `multipart`: `image` и `annotation` — картинка и сцена |

Импорт — единственный вход, который принимает недоверенный файл. Сервер проверяет разметку
по контракту сам, независимо от того, кто её произвёл, и отвечает `422` с `contract_code`
из [contract/README.md](../contract/README.md) (например, `door_not_on_wall`). Хеш картинки
сервер считает сам и сверяет с тем, что написано в разметке. Импорт ничего не перезаписывает:
неудачный черновик — отдельная сцена, её удаляют в корзину. Все двери после импорта закрыты,
освещённость — «светло», «исследовано» пустое.

## Сцены и геометрия

| Метод и путь | Кто | Что делает |
|---|---|---|
| `GET /v1/campaigns/{id}/scenes` | участник | список без скрытых от него сцен |
| `POST /v1/campaigns/{id}/scenes` | мастер | сцена из картинки библиотеки |
| `GET /v1/campaigns/{id}/scenes/{sid}` | участник | состояние; геометрия — только мастеру |
| `PUT /v1/campaigns/{id}/scenes/{sid}/annotation` | мастер | заменить `annotation.json` после проверки контракта; `?version=N` защищает от одновременной правки |
| `PATCH /v1/campaigns/{id}/scenes/{sid}` | мастер | `name`, `light`, `globally_visible`, `active` |
| `POST /v1/campaigns/{id}/scenes/{sid}/duplicate` | мастер | копия состояния, картинка та же |
| `DELETE /v1/campaigns/{id}/scenes/{sid}` | мастер | в корзину; `POST …/restore` возвращает |
| `PUT /v1/campaigns/{id}/scenes/{sid}/walls/{wid}` | мастер | полилиния: `{"points": [[x, y], …]}` |
| `DELETE /v1/campaigns/{id}/scenes/{sid}/walls/{wid}` | мастер | удалить стену |
| `PUT /v1/campaigns/{id}/scenes/{sid}/doors/{did}` | мастер | `{"from", "to", "type", "wall_id"}` |
| `PATCH /v1/campaigns/{id}/scenes/{sid}/doors/{did}` | мастер или игрок рядом | `{"state": "open"}` или `"closed"` |
| `PUT /v1/campaigns/{id}/scenes/{sid}/areas/{aid}` | мастер | `{"type", "polygon"}` |

Правка адресована объекту, поэтому два мастера не мешают друг другу. Дверь в сцене —
состояние: открытая не блокирует ни взгляд, ни путь. Мастер переключает любую дверь, игрок —
только ту, что в пределах одной клетки от своего токена; иначе `403` с текстом «дверь далеко».
`light` — `bright` или `dark`; `active` — какая сцена показана столу, одна на кампанию.

## Токены

| Метод и путь | Кто | Что делает |
|---|---|---|
| `POST /v1/campaigns/{id}/scenes/{sid}/tokens` | мастер | `{"name", "character_id", "x", "y", "size_cells", "darkvision_ft", "hidden"}` |
| `PATCH /v1/campaigns/{id}/scenes/{sid}/tokens/{tid}` | мастер | те же поля, кроме позиции: позиция — движением |
| `DELETE /v1/campaigns/{id}/scenes/{sid}/tokens/{tid}` | мастер | убрать фишку |
| `GET /v1/campaigns/{id}/scenes/{sid}/visibility?character={cid}` | участник | маска для персонажа |

`hidden` — токен не приходит игрокам вовсе, а не «приходит серым». Союзники видны всегда,
но видно фишку, а не комнату вокруг неё. Тёмное зрение — число футов, 0 — его нет.

## Видимость

Маска — растр на всю карту, не зависящий от сетки: 256×256 блоков, блок — сторона картинки,
делённая на 256, две битовые карты (видно, исследовано), по биту на блок, байты построчно
и `base64`. Сетки может не быть вовсе, поэтому клетка для маски не годится.

```json
{
  "character_id": "c1",
  "blocks": 256,
  "visible": "<base64, 8192 байта>",
  "explored": "<base64, 8192 байта>"
}
```

Сервер считает маску для каждого персонажа отдельно: «видно» — пересечение геометрии и света,
«исследовано» — накопленное. Игроку геометрия не уходит: он получает картинку целиком и маску,
а рисунок тумана — дело клиента. Мастер получает геометрию и, по запросу, маску конкретного
персонажа — режим «глазами игроков». Кисти тумана нет ни в API, ни в клиенте: видимое меняется
только стенами, светом сцены, дальностью тёмного зрения и флагом `globally_visible`.

## Стол: WebSocket

`GET /v1/campaigns/{id}/table` с `Upgrade: websocket`, тот же bearer-токен. Первый кадр сервера —
`hello`: `seq`, `time`, `you` (аккаунт, роль, персонаж), `state` (активная сцена, токены, последние
сообщения чата), `actions` — закрытый список того, что человеку сейчас можно. Клиент не хранит
матрицу прав: он показывает то, что пришло.

> **Что уже работает.** `hello` несёт аккаунт, роль, кампанию, `scene_id`, фишки,
> состояние дверей и текущий ход (`turn.token_id`, `turn.round`) сцены (сцена выбирается
> параметром `?scene_id=`, иначе берётся активная). Фишка несёт `owner_id`, `owner_login`,
> `hp`, `hp_max` и `initiative`. `actions` содержит `chat.say`, `token.move`,
> `token.update` и `roll`, а для мастера ещё `token.place`, `scene.show`, `door.set`
> и `turn.next`. Сервер принимает эти намерения; `scene.show` сохраняет активную сцену,
> сбрасывает ход и рассылает `scene.shown` с фишками и дверями новой сцены.
> `token.place` мастера принимает `owner_id` участника; игрок двигает и меняет
> характеристики только своей фишки. `roll` разбирает формулу вида `2d6+3`, бросает
> на сервере и рассылает `roll` с `values`, `modifier` и `total`; `visibility`
> `table`/`self`/`master` решает, кому виден бросок. `turn.next` сортирует фишки по
> инициативе, передаёт ход следующей и увеличивает круг. Игроку сервер присылает
> `visibility` — маску 256×256 из `hello` и после движения фишки, двери или смены сцены;
> считается объединение лучей от его фишек, закрытые двери и стены перекрывают взгляд.
> Бит маски — `x + y*256`, младший бит первым; `1` — видно, `0` — туман.
> Мастеру маска не нужна: он видит геометрию целиком. Для проверки он может
> прислать `visibility.peek` с `account_id` и получить ту же маску с `as_account` —
> режим «глазами игрока»; пустой `account_id` выключает режим. Вместо `path` у `token.move`
> пока передаются `x`, `y` в пикселях картинки. Остальные намерения и события из таблиц
> ниже — контракт на следующие срезы.

**Клиент → сервер: только намерения.**

| `type` | Поля | Кто |
|---|---|---|
| `token.move` | `token_id`, `x`, `y` | игрок — своим, мастер — любым |
| `token.place` | `name`, `owner_id`, `x`, `y` | только мастер: стены не проверяются |
| `token.update` | `token_id`, `hp`, `hp_max`, `initiative` | владелец фишки, мастер |
| `door.set` | `door_id`, `open` | мастер; игрок — дверь рядом |
| `scene.show` | `scene_id` | мастер |
| `turn.next` | — | мастер |
| `visibility.peek` | `account_id` | мастер |
| `roll` | `formula`, `visibility` (`table`/`self`/`master`) | участник |
| `chat.say` | `text`, `channel` (`table`/`master`/`whisper`), `to` | участник |
| `sheet.change` | `character_id`, `changes` | владелец листа, мастер |

Каждое намерение несёт `intent_id`. Ответ — либо событие с результатом, либо отказ
`{"intent_id", "error": {...}}`; после отказа клиент обязан вернуть картинку на место.
Кубы бросает сервер: клиент присылает формулу и модификаторы, а не результат.

**Сервер → клиент: только результат.** У события есть `seq`, `time`, `type`, `actor` и поля
изменения.

| `type` | Что несёт |
|---|---|
| `token.moved` | `token` — объект фишки |
| `token.placed` | `token` — объект фишки |
| `token.updated` / `token.removed` | объект или `token_id` |
| `turn.set` | `token_id`, `round` |
| `door.set` | `door_id`, `state` |
| `scene.changed` | `scene_id`, изменённые поля или объект геометрии |
| `scene.shown` | `scene_id` |
| `visibility` | `mask` (`visible`, `explored`); `as_account` — для режима мастера |
| `roll` | `formula`, `values`, `total`, `visibility`, кому видно |
| `chat.said` | `message_id`, `text`, `channel`, `actor` |
| `sheet.changed` | `character_id`, `changes` |
| `actions` | новый список доступных действий, когда меняется роль или сцена |

**Обрыв и повтор.** Клиент переподключается и присылает `last_seq`; сервер доигрывает
пропущенные события, а если их больше 500 — присылает новый `hello` с полным состоянием.

## Версии и совместимость

- Клиент новее сервера — обычное дело: клиенты обновляются сами, сервер редко. Поэтому клиент
  держит совместимость с несколькими версиями API назад, а если сервер совсем старый — говорит
  это текстом с номером, а не «ошибка подключения».
- Внутри версии сервер не удаляет и не меняет смысл полей, только добавляет. Клиент обязан
  игнорировать незнакомые поля — это ответ сервера, а не вход от недоверенного источника,
  и правило «тишина — не согласие» из [contract/README.md](../contract/README.md) здесь
  не действует.
- Новая версия добавляется рядом (`/v2/`), старая продолжает работать, пока её обслуживает
  сервер. Клиент узнаёт минимум из `426` и показывает «попроси мастера обновить сервер».

## Чего здесь нет

- панели администратора: у неё отдельный вход, порт и описание ([ADMIN.md](ADMIN.md));
- каталога пакетов и раздачи файлов: байты берёт лаунчер из релиза
  ([../launcher/MANIFEST.md](../launcher/MANIFEST.md)), а совместимость версий называет сервер
  при входе;
- голоса и распознавания речи: модель живёт в клиенте, звук не уходит;
- кисти тумана, отката состояния и снимков: правда одна — сцена;
- раздаток и портретов: появятся вместе с файлами кампании, отдельной версией API.
